# QA review — first-hop

## Вердикт: CONCERNS

По ID покрыто всё, по смыслу нет. **Главная дыра — hop#R4 проверен только с одной стороны.** T-hop-04 проверяет только перелёт (2.84 / 2.86 при gap 2.5). Если реализация считает `distance − gap ≤ K4` без модуля, любой недолёт (charge 0 → 1.0 при gap 2.5) засчитается как успешное приземление, и все автотесты останутся зелёными. R4 с допуском 0.35 и есть гипотеза хендоффа, так что это P1.

Скрипт `check_coverage.py`:
```
Тестов: 21 · целей (R/F/E): 20, покрыто 20 · ED: 5 · smoke: 6
Итог: PASS · FAIL 0 · WARN 0
```

## Что покрыто хорошо
- Формулы F1/F2 в hop: типичное значение, верхний кламп, три точки F1 с допуском (T-hop-01…03).
- Edge cases hop E1–E5 и spark E1–E3: у каждого свой сценарий, ожидания конкретные.
- R3 spark «строго больше»: проверено равенство и превышение (T-spark-04).
- Сбой хранилища через `IRecordStorage` в editmode (T-spark-05), это хороший seam.
- DD1–DD3 переданы в playtest-кейсы. Smoke из 6 шагов идёт по критическому пути.
- Типы выбраны верно: логика в editmode, ввод и пауза в playmode.

## Что не ловится

Формат: правило → какой баг пройдёт незамеченным → тест, который его закроет.

### 1. hop#R4: недолёт (P1, главная дыра)
Баг: без `abs` недолёт считается успехом. Баг `≤` → `<` тоже не ловится: тесты стоят на ±0.01 от границы.
- **T-hop-11** (editmode, P1) · Covers hop#R4 · Given gap 2.5, K4 = 0.35 · When distance 2.16 и 2.14 · Then успех, промах.
- **T-hop-12** (editmode, P1) · Covers hop#R4 · Given gap 2.5 · When distance 1.0 (charge 0) · Then промах.

### 2. Переходы состояний hop: половина графа без тестов
Проверены Idle→Charging→Airborne, Charging→Idle (E3, E4) и Dead→рестарт. Не проверены Airborne→Idle (приземление), Airborne→Falling (промах), Falling→Dead (через K5), а также запрещённый ввод в Falling. Баги, которые пройдут: персонаж застревает в Airborne после приземления и второй прыжок невозможен; тап в Falling начинает заряд или рестарт.
- **T-hop-13** (playmode, P1) · Covers hop#R4, hop#R1 · Given Airborne, прыжок в допуск · When конец дуги · Then State = Idle; следующее касание → Charging.
- **T-hop-14** (playmode, P1) · Covers hop#R4, hop#R6 · Given Airborne, прыжок мимо · When конец дуги · Then State = Falling; через K5 ± 1 кадр State = Dead.
- **T-hop-15** (playmode, P2) · Covers hop#R1, hop#R6 · Given Falling · When касание и отпускание · Then State остаётся Falling, charge = 0, рестарта нет.

Кроме того, в T-hop-10 Given противоречит GDD: «Dead» наступает только через K5 = 0.3 с после начала падения, значит «тап через 0.2 с» происходит в Falling, а не в Dead. Ещё тест смешивает две причины упасть: гейт R6 и латентность ED4. Разделить так:
- **T-hop-10a** (playmode, P1) · hop#R6 · Given Falling начался в t0 · When тап в t0 + 0.2 с; тап в t0 + 0.4 с · Then нет рестарта; рестарт.
- **T-hop-10b** (playmode, P1) · ED4 · Given Dead · When тап · Then новый забег (State = Idle на первом фонаре, счёт 0) ≤ 0.3 с от тапа.

### 3. spark: три мутации, которые не заметит ни один тест
- Очки за приземление на фонарь **без** искры. В T-spark-02 в Given не сказано, есть ли искра на фонаре.
  - **T-spark-06** (editmode, P1) · spark#R2 · Given фонарь без искры · When успешное приземление, distance 3.1 · Then счёт не меняется.
- Искра не исчезает (R2, переход Hanging → Collected).
  - **T-spark-07** (editmode, P2) · spark#R2 · Given фонарь с искрой · When успешное приземление · Then искра в состоянии Collected, повторное событие приземления на этот фонарь очков не даёт.
- Счёт не обнуляется при рестарте (R3: «счёт забега»). Smoke-шаг «счёт растёт» этого не поймает.
  - **T-spark-08** (editmode, P1) · spark#R3 · Given забег завершён со счётом 7 · When новый забег · Then счёт = 0, рекорд = max(прежний, 7).
- E2 требует ещё и «нет фидбэка “новый рекорд”» (FB2), а T-spark-04 этого не проверяет.
  - Дополнить T-spark-04: Then при счёте 10 событие NewRecord не вызвано, при 11 вызвано 1 раз.

### 4. Гипотеза хендоффа не превращена в кейс; DD2 не измерить
P1 в плане — это «ломает гипотезу», но самой гипотезы (4 из 5 новичков, 5 успешных прыжков подряд за 3 мин) среди кейсов нет. «Держит дольше для дальнего фонаря» (T-slice-11) без порога не даёт ни pass, ни fail.
- **T-slice-13** (playtest, P1) · Covers DD2, DD3 · Given 5 новичков, первый запуск · When 3 мин игры · Then ≥ 4 из 5 сделали 5 успешных прыжков подряд. Лог: время до серии, число падений до ухода.
- T-slice-11: Then переписать так: «в прыжках 2–3 время удержания для gap > 3.0 ≥ 1.5× удержания для gap < 2.0 у ≥ 4 из 5». Источник: лог hold/gap.

### 5. Латентность ввода и ED1 не проверяются однозначно
В хендоффе §3 и в hop Game Feel записано «отпускание → прыжок ≤ 1 кадр», а теста на это нет. Баг: прыжок стартует через кадр-два, потому что обработка ввода стоит в FixedUpdate. Это ломает «отзывчиво».
- **T-hop-16** (playmode, P1) · Covers hop#R1 · Given Charging, charge 0.5 · When InputTestFixture: отпускание в кадре N · Then в кадре N (не позже N+1) State = Airborne и позиция по X изменилась.

В T-slice-01 ожидание «60 fps, кадр ≤ 16.6 ms» неоднозначно: не сказано, среднее это, p95 или каждый кадр, и какое устройство.
- Then: «устройство <модель> · p95 кадра ≤ 16.7 ms, ни одного кадра > 33 ms за 60 с (Profiler / Frame Timing)».

### 6. Остальное (P2–P3)
- **hop#E3 / K6, только отрицательная сторона.** Если порог завышен (например, K6·10), T-hop-05 пройдёт. **T-hop-17** (editmode, P2) · Given K6 = 0.05 · When отпускание при charge 0.06 · Then State = Airborne.
- **hop#E1 / R5, отпускание в воздухе.** T-hop-07 проверяет только касание, поэтому реализация «игнор press, прыжок на release» пройдёт. Дополнить When: «касание и отпускание в воздухе» · Then «второго прыжка нет, State = Airborne до конца дуги».
- **hop#E5, отпуск первого пальца.** Реализация «прыжок, когда отпущены все пальцы» пройдёт T-hop-09. **T-hop-18** (playmode, P2) · Given Charging первым пальцем, второй прижат · When отпустить первый · Then State = Airborne, charge = holdTime(первый)/K2 ± 0.01. В T-hop-09 Then «заряд продолжается» заменить на число.
- **hop#R3: время полёта 0.5 с не проверено**, хотя T-hop-03 указывает R3 в Covers. **T-hop-19** (playmode, P3) · Given прыжок charge 0.5 · When отпускание · Then приземление через 0.5 ± 1 кадр.
- **spark#F1, граница `>`.** Мутация `>=` не ловится. **T-spark-09** (editmode, P3) · Given K1 = 3 · When distance 3.0 · Then +1.
- **spark#R1, крайние K3.** Тест с seed проверяет только регресс. Добавить детерминированный: K3 = 0 → 0 искр; K3 = 1 → искра на каждом фонаре.
- **ED3 / T-slice-02, «отличимо» субъективно.** Then: «тестер, не глядя на счёт, по звуку называет +1/+2 верно в ≥ 9 из 10». Нужен debug-seed с дальними искрами.
- **ED5 / T-slice-03.** Уточнить When: «force-stop из настроек Android, затем запуск», потому что сворачивание не проверяет запись. T-spark-05 покрывает E3, а не ED5; убрать ED5 из его Covers.
- **Smoke 3 «≤ 0.3 с»** вручную не измерить. Заменить на «рестарт без анимации и ожидания» и сослаться на T-hop-10b.

### Дыры в GDD (не тесты, а вопросы в Open Questions)
- **spark#F1:** `distance` — это дальность прыжка (hop#F1) или расстояние до фонаря? При K4 = 0.35 перелёт 3.1 на фонарь в 2.9 даст двойную искру на «ближнем» фонаре. Summary и ED3 говорят «дальний фонарь». Пока ответа нет, T-spark-02 проверяет неизвестно что.
- **hop:** касание началось в воздухе и держится после приземления. Начинается ли заряд? R1 допускает оба прочтения.
- **hop#E4:** считается ли потеря фокуса без паузы (шторка уведомлений Android) сворачиванием?
