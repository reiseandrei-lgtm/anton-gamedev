# gdd-author

## Вход
Имя системы (аргумент). Прочитай: `design/pillars.md`, строку системы в `design/systems-map.md`, GDD систем-зависимостей (только Summary и Interactions), существующий `design/gdd/<system>.md`, если есть.

## Режимы
- **Полный** (новая система): шаблон `references/gdd-template.md` целиком.
- **Лёгкий** (правка существующей, тюнинг, мини-механика): блок Quick Spec — что меняется, зачем (столп), новые правила, затронутые формулы/knobs, риски. Дописывается в конец GDD системы в раздел «Changes» и в `decisions-log.md`.

## Процедура (полный режим)
1. Создай файл со скелетом всех секций, `status: draft`.
2. Иди по секциям в порядке: Summary → Player Fantasy → Core Rules → States → Interactions → Formulas → Edge Cases → Dependencies → Tuning Knobs → Feedback (visual/audio) → Game Feel → Open Questions.
3. Для каждой секции: сначала спроси пользователя о решениях (по одному-два вопроса), потом структурируй его ответы. Не придумывай правила за него — предлагай 2–3 варианта разного риска с дешёвой проверкой, если он просит; помечай их ГИПОТЕЗА. «Просто сделай» → заполни целиком, допущения помечай ГИПОТЕЗА (`../gd-router/references/principles.md`).
4. Всё неизвестное → `Open Questions`, не «TBD» внутри правил.
5. Формулы: переменные, диапазоны, ожидаемый выход, клампы.
6. Ссылка на столп в шапке обязательна.
7. Стабильные ID: правила `R1…`, формулы `F1…`, edge cases `E1…`, knobs `K1…`, feedback `FB1…`. При правке ID не перенумеровываются, удалённый не переиспользуется. На них ссылаются `qa-plan`, `tech-design`, `audio-direction` как `<system>#<ID>`. Старый GDD без ID — при первой правке проставь ID (с подтверждения).

## Выход
`design/gdd/<system>.md`. В конце — чек-лист готовности к ревью (из шаблона) и рекомендация `/gd:review design/gdd/<system>.md`.

## Правила
Язык ответа = язык запроса. Художественный текст (реплики, флейвор-тексты, описания предметов) — только по явной просьбе; вместо него плейсхолдер `[ТЕКСТ: назначение]`. Без воды: правила однозначны, программист реализует без вопросов.
