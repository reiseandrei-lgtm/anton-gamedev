# Шаблоны документов

Используй, когда результат работы — документ, а не разговор. Шаблоны задают структуру, не длину: одностраничная спека, которую прочитают, полезнее пятнадцатистраничной.

## Содержание

1. Mode spec
2. Ability / role spec
3. Design review
4. Раздел GDD
5. One-pager питч

---

## 1. Mode spec

```markdown
# Режим: [Название]

**Одна строка:** [что игрок делает и почему это весело]
**Социальное решение:** [какое решение о других игроках создаёт режим]
**Pillars:** [какие из четырёх усиливает]

## Правила
[Нумерованный список. Каждое правило — одно предложение. Числа с пометкой «стартовая точка».]

## Победа и завершение
[Условие победы, длительность, что происходит при неполном лобби]

## Роль сцепления
[Когда сцепляться выгодно, когда — нет, какова цена разрыва]

## Без голоса
[Как режим играется через пинги и эмоции]

## Cold start
[Что происходит при 4 игроках вместо 10]

## Как проверить
| Гипотеза | Метрика | Ожидаемый сигнал | Что делаем, если не подтвердится |
|---|---|---|---|

## Открытые вопросы
[Список. Не растворять в тексте.]
```

## 2. Ability / role spec

```markdown
# Роль: [Название]

**Фантазия:** [одно предложение от лица игрока]
**Асимметрия:** [что она делает такого, чего не делает никто]

## Способность
- Эффект внутри связки:
- Эффект вне связки:
- Ресурс и как он восполняется:
- Кулдаун / стоимость: [стартовая точка, обоснование]

## Решение для группы
[Кого присоединить, кого отсоединить, кто ведёт, когда рискнуть разрывом]

## Соло-полезность
[Роль обязана работать и вне связки]

## Читаемость
[Как игрок за долю секунды понимает: кто применил, на кого, с каким эффектом — визуал, звук, силуэт]

## Контрплей
[Что делает противник]

## Риски
[Где ломается, где становится обязательной, где скатывается в статбонус]
```

## 3. Design review

Порядок фиксированный: сначала что работает, потом что ломается, потом что делать. Не смягчать.

```markdown
# Ревью: [что ревьюим]

## Вердикт
[Один абзац. Если механика противоречит north star — сказать здесь.]

## Что работает
[Конкретно, с объяснением почему]

## Что ломается
| Проблема | Почему это важно | Альтернатива |
|---|---|---|

## Проверка по чек-листу
[Прогон по чек-листу из design-heuristics.md, только пункты с проблемами]

## Что делать дальше
[2–3 действия, отсортированные по соотношению эффект/стоимость]
```

## 4. Раздел GDD

Пиши в стиле существующего концепт-документа проекта: короткие тезисы в таблицах, явная маркировка уровня достоверности (ФАКТ / РЕКОНСТРУКЦИЯ / ГИПОТЕЗА), схемы описываются текстом с номером и подписью.

```markdown
## [Номер]. [Название раздела]

[Вводный абзац: зачем этот раздел и что он решает]

| **ТЕЗИС 01** [Формулировка] | **ТЕЗИС 02** [Формулировка] |
| --- | --- |

**[Подраздел]**
[Содержание]

| **Ключевой принцип** [Одна мысль, которую надо запомнить] |
| --- |

**Открытые вопросы**
[Список]
```

## 5. One-pager питч

Для инвесторов и партнёров. Один экран, без жаргона, ведёт эмоцией, а не механикой.

```markdown
# SYNCARIO

[Абзац от второго лица: кто игрок, что с ним происходит, чем это заканчивается.
Заканчивать социальным обещанием, а не фичей.]

**Жанр:** [строка]
**USP:** [строка]
**Core loop:** найти → сцепиться → договориться → решить задачу → пересобрать связку → сохранить контакт
**Платформа:** [строка]
**Статус:** [честный, без приукрашивания]
```
