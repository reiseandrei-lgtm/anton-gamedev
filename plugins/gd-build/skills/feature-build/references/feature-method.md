# feature-build: как реализовать систему майлстоуна

Свой документ. Обобщает `slice-build` на систему; verify loop — `../../slice-build/references/verify-loop.md` (адаптация unity-kit, MIT, см. ATTRIBUTION.md).

## 1. Разбор входа
| Что прочитать | Зачем |
|---|---|
| GDD: Core Rules, States & Transitions, Formulas, Edge Cases | список ID, которые должны стать ✅ |
| GDD: Interactions | какие события и данные система получает от готовых систем и отдаёт им |
| `tech/architecture.md`: Modules | asmdef, от чего модуль может зависеть (циклов нет) |
| `tech/architecture.md`: Config map | какие knobs → какой конфиг и поле |
| `tech/architecture.md`: Test seams | где проверяется правило: EditMode-класс или PlayMode + read-only свойство |
| Тест-план | T-ID, Given / When / Then — это и есть тест |
| Хендофф майлстоуна | `ED-<system>-N` и порядок систем |

Неясность в GDD (правило молчит о случае, который встретился в коде) — не решать самому. Записать вопрос в Open Questions GDD, в лог — ⛔ «не выполнено: вопрос дизайнеру», предложить `gd:gdd-author --quick`.

## 2. Порядок задач
1. Модуль и asmdef (если нет) → конфиг-классы по Config map → ассеты конфигов с числами из GDD (Current).
2. Чистая логика (формулы, переходы состояний) — EditMode-тесты первыми.
3. Компоненты и интеграция с другими системами — PlayMode-тесты (ввод — `InputTestFixture`, `queueEventOnly: true`).
4. Сцена / префабы — через MCP (`manage_scene`, `manage_gameobject`, `manage_components`), не правкой YAML.
5. Smoke системы в play mode: пробы read-only свойств, скриншот, консоль, `Time.frameCount`.

## 3. Доказательства в логе
| Статус | Когда | Пример |
|---|---|---|
| ✅ | тест зелёный / замер / скриншот, на который ты посмотрел | `T-chain-02 зелёный (EditMode); красный до реализации` |
| ⚠️ | сделано, но не проверено (режим plan, нет устройства) | `реализовано, не проверено в редакторе` |
| ⛔ | не сделано | `не выполнено: GDD не говорит, что при … (Open Questions)` |

Красный прогон до реализации — часть доказательства: тест, который не падал без кода, ничего не доказывает.

## 4. Передача ревьюеру
- `git diff` от последнего коммита до начала работы над системой, только папки модуля, тестов и конфигов системы.
- Агенту — только пути (diff, GDD, `tech/architecture.md`, тест-план). Лог сборки не передавать: ревьюер проверяет код, а не твои ✅.
- FAIL ревью → исправление → новый diff → повторное ревью. CONCERNS — решение пользователя, записать в лог (Open issues).

## 5. Частые ошибки
- Knob литералом «пока»: потом его никто не найдёт. Сразу в конфиг.
- Тест проверяет реализацию, а не правило (сравнивает с тем же выражением, что в коде).
- Связь с другой системой через `FindObjectOfType` в `Update` вместо события.
- «Работает» по консоли без проверки mtime DLL.
- Класс `ScriptableObject` / `MonoBehaviour` в файле с другим именем (`ChainConfig` внутри `ChainGenerator.cs`): Unity не связывает ассет со скриптом, `manage_scriptable_object` создаёт «пустой» ассет, `Resources.Load<T>` возвращает null. Один такой класс — один файл с его именем; после создания ассета проверь `m_Script` и загрузку в тесте.
- PlayMode-тест без уборки (`[UnityTearDown]`): после исключения объекты теста живут дальше, и их `Update` роняет соседние тесты.
