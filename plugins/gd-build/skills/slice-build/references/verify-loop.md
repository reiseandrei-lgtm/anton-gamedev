# Verify loop: как доказать, что Unity-изменение работает

> Адаптировано из unity-kit `unity-verify`, `unity-playtest` (MIT © 2026 Benjamin Curlier). См. ATTRIBUTION.md. Привязка к ED / T-ID и лог сборки — свои. Имена инструментов — по CoplayDev/unity-mcp; соответствие другим MCP — `mcp-actions.md`.

## 1. Компиляция (после любого изменения .cs)
1. Дождись конца компиляции: состояние редактора `is_compiling == false`. Но `false` выглядит одинаково для «закончил» и «не начинал».
2. **Доказательство**: mtime `Library/ScriptAssemblies/<Module>.dll` новее mtime изменённых исходников. DLL старше исходника → читаешь устаревшую сборку, что бы ни говорила консоль. Форсируй компиляцию (refresh с `mode: force`, `scope: all`, `compile: request`) и проверь снова. Редактор без фокуса сам не обновляет ассеты, а refresh без `force` может ничего не скомпилировать.
3. Подтверждение: `grep "error CS"` по логу редактора. Лог общий для всех проектов и лежит не в проекте: Windows `%LOCALAPPDATA%\Unity\Editor\Editor.log`, macOS `~/Library/Logs/Unity/Editor.log`, Linux `~/.config/unity3d/Editor.log`. В headless-прогоне — файл из `-logFile`. В `Logs/` проекта лога редактора нет.
4. Консоль: ошибки. Любая ошибка компиляции — стоп: чини и перепроверяй (одна ошибка часто прячет следующую). **Тесты при ошибках компиляции не запускай**: `run_tests` молча выполнит старую DLL и покажет старый результат. Шум самого MCP (строки с `MCP-FOR-UNITY` о переподключении клиента) — не ошибка компиляции.
5. После компиляции идёт domain reload, и мост MCP на несколько секунд отключается («No Unity instances connected»). Дождись переподключения (проба связи), потом следующий вызов.
6. Затем предупреждения: свои новые — чинить, если тривиально, иначе в лог.

## 2. Тесты (когда изменилось поведение)
1. EditMode для чистой логики, PlayMode для жизненного цикла, физики, сцен, ввода.
2. Прогон возвращает задачу — опрашивай с таймаутом 30–60 с; PlayMode медленнее, редактор без фокуса может тормозить.
3. **0 выполненных тестов = провал**, а не зелёный: чаще всего тестовая asmdef без `UnityEngine.TestRunner` / `UnityEditor.TestRunner` или ссылка на несуществующую сборку.
4. Зависшая задача с `completed=0`, редактор снова в edit mode, открыта `InitTestScene` → упал сам Test Framework: перезагрузи рабочую сцену, повтори; повторилось → перезапуск редактора. Удалить оставшиеся `Assets/InitTestScene*` перед коммитом.
5. Падающий тест после твоего изменения — твоя проблема, даже если «выглядит не связанным».
6. T-ID теста — имя метода `T_hop_01_…` или `[NUnit.Framework.Property("TID", "T-hop-01")]`. `[Category("T-hop-01")]` не годится: NUnit запрещает «-» в категориях, тест падает, не начавшись.
7. `"testables": ["com.unity.inputsystem"]` добавляет в PlayMode-прогон тесты самого пакета (4 штуки в Input System 1.20). Считай свои тесты по T-ID, пакетные — отдельной строкой.

## 3. Ввод (если слайс управляется игроком)
- Единственный надёжный способ симулировать ввод — PlayMode-тест от `InputTestFixture` (asmdef: `Unity.InputSystem`, `Unity.InputSystem.TestFramework`; сборка появляется только при `"testables": ["com.unity.inputsystem"]` в `Packages/manifest.json`). Минимум: одно действие меняет состояние, один недопустимый ввод отвергнут, один переход в конечное состояние (смерть / цель / рестарт).
- `BeginTouch` / `Press` по умолчанию обрабатывают событие сразу, в кадре теста, и к `Update` игры `wasPressedThisFrame` уже false. Для кода, который читает `wasPressedThisFrame` в `Update`, передавай `queueEventOnly: true`: событие обработается в начале следующего кадра, как у живого игрока.
- Не пытайся симулировать клавиши живьём через `execute_code` в play mode: события ввода глушатся без фокуса окна Game.
- «Ввод ничего не делает»: 1) `InputSystem.devices.Count == 0` при исключении от старого `Input.*` → редактор не перезапустился после смены Active Input Handling; 2) код молча выходит на `Keyboard.current == null`; 3) у пользователя нет фокуса на Game view.

## 4. Play-mode smoke и скриншот
1. Перед Play проверь активную сцену (после перезапуска редактор может открыть пустую Untitled). Play → несколько секунд → консоль на исключения → Stop. **Никогда не оставляй play mode включённым.**
2. Сравни `Time.frameCount` в начале и конце: редактор без фокуса не тикает, чистая консоль за 0 кадров ничего не доказывает.
3. Проба состояния — через публичные read-only свойства (`IsGrounded`, `Score`). Нет свойства — добавь (это seam из `tech/architecture.md`).
4. Геймплей веди на уровне намерения: вызывай тот же метод, что и обработчик ввода. Задержка MCP — секунды: замедли или заморозь тик перед пошаговой пробой и восстанови после (`Time.timeScale = 0` → действие с явным временем, например `Press` → `Tick(hold)` → `Release` → `Time.timeScale = 1`).
5. Перед скриншотами выставь в Game view соотношение сторон целевой платформы (портрет для мобайла): иначе проверяешь не тот кадр, что увидит игрок.
6. Скриншот Game view на старте, после действия и в конечном состоянии. **Посмотри на картинку**: состояние говорит одно, пиксели — другое (пример: `text` лейбла не присвоен — все пробы зелёные, на экране пусто).

## 5. Ограничение попыток
3 цикла «правка → проверка» на одну проблему. Одинаковый текст ошибки дважды — стратегия неверна: смени подход осознанно или остановись и отчитайся. Честное «застрял после 3 попыток» лучше десяти тихих правок одного файла.

## 6. Как отчитываться
Не «готово», а «консоль чистая, EditMode 6/6, PlayMode 2/2, smoke OK за 240 кадров, скриншот: игрок на платформе, счёт 0». Пропущенный шаг назови явно. Утверждения — с доказательством; где данных мало — так и скажи, не округляй до PASS.
